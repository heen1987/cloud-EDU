IaaS 구축
— 콘솔로 만들어보고, 코드로 자동화하기

3강에서 배운 VPC·Subnet·Instance 개념을 NHN Cloud 콘솔에서 직접 클릭해 쿠버네티스 클러스터용 서버 5대를 만들고, 그 다음 동일한 인프라를 Terraform 코드로 선언해 재현 가능하게 만드는 실습형 강의입니다.

원본: 4.2026년 새싹(SeSAC) 클라우드 네이티브 교육 자료(IaaS 구축).pdf (66p) 구성: 콘솔 실습 → IaC(Terraform) 실습 핵심 키워드: NHN Cloud · VPC/Subnet · Floating IP · Terraform · IaC

이 강의를 보는 순서

  1. 왜 직접 손으로 만들어보는가 — 3강에서 개념으로만 배운 VPC/Subnet/Instance/Floating IP를 실제로 클릭해보며 리소스 간 의존관계(서브넷은 라우팅 테이블 연결 필수, 인스턴스는 중지해야 NIC 추가 가능 등)를 몸으로 확인한다
  2. 무엇을 만드는가 — Kubernetes 클러스터용 인스턴스 5대(Control Plane 1 + Worker 3 + NFS 1)라는 구체적 목표
  3. 어떻게 만드는가 — Part Ⅰ: NHN Cloud 콘솔 클릭으로 먼저 만들어본다 → Part Ⅱ: 동일한 결과물을 Terraform 코드로 선언해 재현한다
  4. 핵심 정리 — 콘솔 방식과 코드(IaC) 방식의 차이를 비교하고, 다음 강의(5강 · K8S 클러스터 설치)에서 이 5대 서버 위에 실제 쿠버네티스를 올린다
PART Ⅰ

콘솔 기반 IaaS 구축 (NHN Cloud)

3강에서 개념으로 배운 VPC·Subnet·Instance·Floating IP를 NHN Cloud 콘솔에서 직접 클릭하며, Kubernetes 클러스터에 필요한 서버 5대(Control Plane 1 + Worker 3 + NFS 1)를 만듭니다.

01 · 실습 목표와 전체 그림

이번 실습의 목표는 하나입니다 — Control Plane(마스터) 1대, Worker 3대, NFS 1대, 총 5대의 우분투 22.04 서버를 NHN Cloud(OpenStack 기반 퍼블릭 클라우드) 위에 만드는 것입니다. 콘솔 접속 → 네트워크(서브넷) 준비 → 인스턴스 5대 생성 → 플로팅 IP로 외부 접속 통로 확보 → 네트워크 인터페이스 추가 구성 → SSH 접속까지, 실제 클라우드 인프라를 구축하는 전체 흐름을 한 번씩 손으로 거칩니다.

  • 대상 플랫폼: NHN Cloud (OpenStack 기반 퍼블릭 클라우드), 콘솔 https://opa.console.nhncloud.com/
  • 구축 대상: Kubernetes 클러스터용 인스턴스 5대 — Control Plane 1 + Worker 3 + NFS 1
💬쉽게 말하면

서버 5대를 역할별로 나눠 만든다고 생각하면 쉽습니다. Control Plane은 "관제탑"(클러스터 전체 상태를 지켜보고 지시를 내리는 역할), Worker는 "현장 작업자"(실제 작업을 처리하는 서버 3대), NFS는 "공용 창고"(여러 작업자가 함께 쓰는 파일을 보관하는 서버)에 비유할 수 있습니다. 이번 시간에는 이 5대의 빈 서버를 만드는 것까지만 하고, 그 위에 실제 쿠버네티스(관제탑 소프트웨어)를 설치하는 것은 다음 강의에서 진행합니다.

?왜 콘솔로 먼저 만들어보는가

인프라를 코드로 자동화(Part Ⅱ의 Terraform)하기 전에 반드시 콘솔에서 직접 만들어보는 이유가 있습니다. 서브넷은 라우팅 테이블에 연결해야 하고, 인스턴스에 네트워크 인터페이스를 추가하려면 먼저 인스턴스를 중지해야 하는 등, 리소스마다 숨어 있는 순서와 의존관계는 문서만 봐서는 잘 와닿지 않습니다. 콘솔에서 클릭 한 번 한 번 직접 겪어봐야 '이 순서가 왜 필요한지'를 체감하고, 그래야 이후 이 과정을 Terraform 코드로 옮길 때 무엇을 자동화해야 하는지 정확히 알 수 있습니다.

◎실무에서 어떤 상황에 적용되는가

쿠버네티스 클러스터를 자체 구축(온프레미스/사설 클라우드)할 때 최소 구성이 바로 이 형태입니다 — 클러스터 상태를 관리하는 Control Plane 노드, 실제 워크로드(파드)를 실행하는 Worker 노드 여러 대, 그리고 여러 노드가 파일을 공유해야 할 때 쓰는 NFS 노드. 이 실습에서 만드는 5대 구성은 다음 강의(5강)에서 Kubespray로 실제 쿠버네티스를 설치할 대상 서버이기도 합니다.

대시보드 접속 → 네트워크 설정 → 인스턴스 생성 및 설정(+플로팅 IP) → 네트워크 인터페이스 설정 → 인스턴스 접속 순서로 진행합니다.

02 · 대시보드 접속

◎실무에서 어떤 상황에 적용되는가

이 콘솔은 OpenStack 기반의 NHN Cloud 퍼블릭 클라우드지만, '대시보드 로그인 → 프로젝트 선택 → 리소스 메뉴' 라는 구조 자체는 AWS/Azure/GCP 등 다른 퍼블릭 클라우드 콘솔에도 그대로 적용되는 공통 패턴입니다.

  1. 콘솔 접속

    https://opa.console.nhncloud.com/ 접속 → 메일로 수신된 NHN Cloud 계정안내메일에서 비밀번호를 변경하여 로그인.

  2. 프로젝트 선택

    로그인 후 대시보드 진입 → 프로젝트 목록에서 배정된 프로젝트(예: "숭실대학교" 프로젝트) 선택.

03 · 네트워크 설정 — 서브넷 생성 · 라우팅 테이블 연결

?왜 이 작업을 하는가

VPC(가상 네트워크 공간)는 프로젝트에 이미 준비되어 있지만(Default Network, 192.168.0.0/16), 그 큰 대역을 그대로 쓰면 다른 교육생과 IP가 겹칩니다. 그래서 VPC 안에서 내가 쓸 IP 구간만 별도로 잘라내는 것이 서브넷 생성입니다. 서브넷을 만든 뒤 라우팅 테이블에 연결하지 않으면 이 서브넷은 외부(인터넷)와 통신할 경로가 없는 '고립된 네트워크'로 남습니다 — 3강에서 배운 'Routing은 Internet Gateway와 연결 필수'라는 제약이 여기서 그대로 적용됩니다.

💬쉽게 말하면

아파트 단지에 비유하면 이해하기 쉽습니다. VPC는 "단지 전체 부지", 서브넷은 그 부지 안에서 내가 배정받은 "한 개 동"입니다. 그런데 동을 새로 지어도 정문 출입 명단(라우팅 테이블)에 등록하지 않으면 그 동 주민은 단지 밖으로 나갈 수 없는 것과 같습니다 — 그래서 서브넷을 만든 직후 반드시 라우팅 테이블 연결까지 해줘야 외부(인터넷)와 통할 수 있습니다.

  1. 서브넷 생성

    [Network] → [Subnet] → [서브넷생성] 클릭 → VPC(Default Network, 192.168.0.0/16) 선택 → 이름 edu{교육생번호}-subnet 입력 → CIDR을 VPC 범위 내에서 설정(예: 192.168.1.0/24).

  2. 생성 확인

    서브넷 생성 성공 팝업 확인.

  3. 라우팅 테이블 연결

    [Network] → [Subnet] 목록에서 방금 만든 서브넷 체크 → [라우팅테이블연결] 클릭 → 예시와 동일한 라우팅 테이블인지 확인.

아래는 VPC 대역 안에서 교육생별 서브넷 CIDR을 어떻게 나눠 쓰는지 보여주는 값 예시입니다.

VPC network        : 192.168.0.0/16 (Default Network)
서브넷 CIDR 예시1   : 192.168.1.0/24  (192.168.1.1 ~ 192.168.1.255)
서브넷 CIDR 예시2   : 192.168.2.0/24  (192.168.2.1 ~ 192.168.2.255)
이름 규칙           : edu{교육생번호}-subnet
⚙왜 CIDR을 VPC 범위 안에서만 정해야 하는가

서브넷은 VPC라는 큰 IP 대역을 잘라서 쓰는 것이므로, 서브넷의 CIDR은 반드시 VPC의 CIDR 범위 안에 있어야 합니다(예: VPC가 192.168.0.0/16이면 서브넷은 192.168.0.0~192.168.255.255 범위 안에서만 만들 수 있습니다). 이 규칙이 있기 때문에 같은 VPC를 함께 쓰는 여러 교육생이 각자 다른 서브넷 대역(192.168.1.0/24, 192.168.2.0/24 …)을 나눠 가져도 IP가 서로 겹치지 않습니다.

!주의

서브넷을 만들어도 라우팅 테이블에 연결하지 않으면 이후 인스턴스에 플로팅 IP를 연결해도 외부에서 접속할 수 없습니다. 순서를 헷갈리지 않도록 서브넷 생성 직후 바로 라우팅 테이블 연결까지 마치는 것이 안전합니다.

04 · 인스턴스 생성 및 설정

?왜 이 작업을 하는가

5대를 한 번에 만드는 이유는 쿠버네티스 클러스터의 최소 구성 때문입니다. 클러스터 상태를 관리하는 Control Plane(마스터) 1대, 실제 워크로드를 실행하는 Worker 노드 3대, 그리고 여러 노드가 파일을 공유할 때 쓰는 NFS 노드 1대 — 역할이 다른 노드를 처음부터 구분해서 만들어 두어야 다음 강의에서 각 노드에 알맞은 쿠버네티스 구성요소(마스터 컴포넌트 vs kubelet)를 설치할 수 있습니다.

  1. 메뉴 진입

    [Compute] → [Instance] → [인스턴스생성] 클릭.

  2. 이미지 선택

    공용 이미지 탭에서 검색어 ubuntu 입력 → Ubuntu Server 22.04 LTS 선택.

  3. 인스턴스 정보 입력

    가용성 영역 kr-pub-a, 인스턴스 이름 edu{교육생번호}-cluster, 인스턴스 타입 r2.c2m8(검색어 r2로 빠르게 찾기), 인스턴스 수 5, 루트 블록 스토리지 SSD 50GB.

  4. 키페어 생성

    키페어 이름 K-PaaS-Key{교육생번호} 입력 → [키페어생성] 클릭.

  5. 키페어 다운로드

    생성된 .pem 파일을 다운로드하여 분실·삭제되지 않도록 안전하게 보관.

  6. 네트워크 설정

    [네트워크설정]에서 앞서 만든 교육생 서브넷(edu{번호}-subnet) 선택.

  7. 최종 확인 & 생성

    이미지/가용성영역/이름/타입/인스턴스 수 5/키페어/스토리지/서브넷 값을 재확인 → [인스턴스생성] 클릭.
⚙인스턴스 수를 5로 지정하면 내부적으로 무슨 일이 일어나는가

'인스턴스 수'에 5를 입력하면 콘솔은 입력한 이름을 접두어로 사용해 edu1-cluster1~edu1-cluster5처럼 순번이 붙은 5개의 개별 인스턴스를 동시에 프로비저닝합니다. 이 5대는 이미지·타입·루트스토리지·서브넷 설정을 동일하게 공유하지만, 각각 서로 다른 사설 IP를 자동으로 할당받습니다. 다만 이 시점에는 아직 '어떤 인스턴스가 Control Plane인지'는 구분되지 않으므로, 이후 단계(플로팅 IP 연결)에서 사람이 직접 하나를 Control Plane으로 지정해 줍니다.

!주의

키페어(.pem)는 생성 시점에만 다운로드할 수 있고 이후에는 다시 받을 수 없습니다. 최초 생성 시 반드시 안전한 곳에 백업해야 하며, 분실 시에는 인스턴스에 새 키를 연결하는 별도 절차가 필요합니다.

05 · 플로팅 IP 설정 (Control Plane 전용)

?왜 이 작업을 하는가

지금까지 만든 5대 인스턴스는 모두 사설 IP(예: 192.168.1.x)만 가지고 있습니다. 사설 IP는 VPC 내부에서만 통하는 주소라서, 로컬 PC에서 인터넷을 거쳐 이 서버에 SSH로 접속하려면 공인 IP가 필요합니다. 이 역할을 하는 것이 Floating IP입니다.

💬쉽게 말하면

회사 전화에 비유하면, 사설 IP는 직원 개개인의 "내선번호"(회사 안에서만 통하는 번호)이고 플로팅 IP는 외부에서 걸 수 있는 "대표번호"(공인 IP)입니다. 이 실습에서는 대표번호(플로팅 IP)를 Control Plane 한 대에만 연결해 두고, Worker·NFS는 내선번호(사설 IP)만 갖게 합니다.

  1. 인스턴스 선택

    인스턴스 목록에서 Control Plane으로 쓸 인스턴스(예: edu1-cluster1) 체크 → [플로팅 IP 관리] 클릭.

  2. 플로팅 IP 생성/연결

    원하는 IP가 없으면 [+생성] 클릭 → 생성된 플로팅 IP와 네트워크 인터페이스(해당 인스턴스) 선택 → [연결] 클릭.

  3. 연결 확인

    인스턴스 목록에서 해당 인스턴스에 플로팅 IP가 표시되는지 확인.
◎실무에서 어떤 상황에 적용되는가

Control Plane 노드 1대에만 플로팅 IP를 연결하는 것이 일반적인 구성입니다. Worker·NFS 노드는 클러스터 내부 통신만 하면 되므로 사설 IP만으로 충분하고, 외부에서는 플로팅 IP를 가진 Control Plane을 통해 먼저 접속한 뒤 내부망으로 다시 SSH 접속하는 방식을 씁니다(07 · 인스턴스 접속에서 실제로 사용).

06 · 네트워크 인터페이스 설정

?왜 이 작업을 하는가

Control Plane 노드에 HA(고가용성) 구성이나 별도 용도(Ingress 등)를 위한 추가 네트워크 통로가 필요할 때, 인스턴스를 새로 만들지 않고 기존 인스턴스에 네트워크 인터페이스(NIC)만 추가로 붙일 수 있습니다. 이번 실습에서는 이 절차 자체(별도 NIC 생성 → 기존 인스턴스에 연결)를 연습합니다.

  1. 인터페이스 생성

    [Network] → [Network Interface] → [네트워크인터페이스생성] 클릭 → 이름 edu{번호}-Ingress 입력 → VPC/서브넷은 Control Plane 노드와 동일한 것 선택(사설 IP 자동 할당) → [확인].

  2. 플로팅 IP 연결(선택)

    생성한 인터페이스에도 필요 시 플로팅 IP를 생성/연결.

  3. 대상 인스턴스 중지

    [Compute] → [Instance]에서 Control Plane 노드 선택 → [...] 메뉴 → [인스턴스중지]. 인스턴스를 중지하지 않으면 '네트워크 인터페이스 연결 추가' 버튼이 활성화되지 않습니다.

  4. 인터페이스 연결 추가

    중지된 인스턴스 클릭 → [네트워크] 탭 → [네트워크인터페이스연결추가] 클릭.

  5. 기존 인터페이스 지정

    [기존 네트워크 인터페이스 지정] 선택 → 1번에서 만든 인터페이스(edu{번호}-Ingress) 선택 → 확인.

  6. 인스턴스 재시작

    [인스턴스시작] 클릭.
⚙왜 반드시 인스턴스를 중지해야만 NIC를 추가할 수 있는가

가상 서버에 네트워크 카드를 새로 꽂는 작업은 물리 서버로 치면 하드웨어 구성을 바꾸는 것과 같습니다. OpenStack은 실행 중인 인스턴스의 네트워크 구성이 예기치 않게 바뀌는 것을 막기 위해, NIC를 추가하려면 먼저 인스턴스를 중지 상태로 만들도록 강제합니다.

💬쉽게 말하면

달리는 차에 부품을 새로 장착할 수 없는 것과 같은 이치입니다. 컴퓨터에 랜카드(NIC)를 하나 더 꽂으려면 전원을 끄고 작업하는 것처럼, 인스턴스도 네트워크 인터페이스를 추가하려면 먼저 멈춰(중지) 세워야 합니다. 즉, "네트워크인터페이스연결추가" 버튼이 안 눌린다면 아직 인스턴스를 중지하지 않았다는 뜻입니다.

!주의

실습 중 가장 흔한 실수 — 인스턴스를 중지하지 않은 채로 '네트워크 인터페이스 연결 추가' 버튼을 찾다가 비활성화되어 있는 것을 보고 당황하는 경우가 많습니다. 반드시 [...]→[인스턴스중지]를 먼저 실행하세요.

07 · 인스턴스 접속 (SSH)

?왜 이 작업을 하는가

Worker·NFS 노드는 플로팅 IP(공인 IP)가 없기 때문에 로컬 PC에서 곧바로 SSH 접속할 수 없습니다. 그래서 플로팅 IP를 가진 Control Plane에 먼저 접속한 뒤, 같은 사설망 안에서 Control Plane이 다시 Worker/NFS로 SSH 접속하는 '점프 호스트(Jump Host)' 패턴을 사용합니다.

  1. 키 내용 복사

    인스턴스 생성 시 다운로드한 K-PaaS-Key.pem 파일을 열어 키 내용 전체를 복사.

  2. Control Plane 접속

    SSH 클라이언트(Xshell/MobaXterm)에서 프로토콜 SSH, 사용자명 ubuntu, 호스트에 Control Plane 플로팅 IP 입력, 접속 방법 Public Key → 로컬의 K-PaaS-Key.pem 지정 후 접속.

  3. Control Plane 내부에 키 사본 생성

    vim {파일명}.pem 실행 → Insert 모드(i)로 전환 → 로컬에서 복사한 키 내용 붙여넣기 → Esc → :wq!로 저장 후 종료. (파일명은 Pem Key 이름과 동일하게 설정)

  4. 권한 변경

    chmod 600 {pem키파일명} (실행하지 않으면 SSH 접속 시 에러 발생).

  5. Worker/NFS 노드 접속

    ssh -i {pem키파일명} ubuntu@{워커노드 사설 IP}.

이 코드가 하는 일을 한 줄로 요약하면: Control Plane 안에 pem 키 사본을 만들고, 접속에 필요한 권한을 맞춘 뒤, 그 키로 내부망의 Worker 노드에 다시 접속하는 3단계 명령어입니다.

# Control Plane 내부에서 키 사본 만들기
$ vim K-PaaS-Key3.pem
# i 로 Insert Mode 전환 → 로컬에서 복사한 키 내용 붙여넣기 → Esc → :wq! 로 저장 후 종료

# Pem Key 권한 변경 (안 하면 SSH 접속 시 에러)
$ chmod 600 K-PaaS-Key3.pem

# Worker 노드로 접속 (Control Plane 내부에서 실행)
$ ssh -i K-PaaS-Key3.pem ubuntu@192.168.3.29
ubuntu@edu1-cluster2: ~

예시 화면 · 참고용 접속에 성공하면 이런 환영 메시지(MOTD)와 함께 프롬프트가 접속한 워커 노드 것으로 바뀐다. 실제 배너의 세부 문구·시스템 통계는 우분투 버전과 서버 상태에 따라 다르다.

⚙왜 Pem Key를 Control Plane 안에도 복사해 둬야 하는가

모든 인스턴스는 생성 시 동일한 키페어(K-PaaS-Key)로 만들어졌기 때문에, Worker/NFS 접속에도 같은 개인키가 필요합니다. 로컬 PC의 키를 Worker에 직접 쓸 수는 없으므로(Worker는 플로팅 IP가 없어 로컬에서 직접 도달 불가), 이미 접속해 있는 Control Plane 내부에 키 사본을 만들어 두고, 그 사본으로 내부망을 통해 Worker/NFS에 다시 접속하는 것입니다.

!주의

chmod 600을 하지 않으면 SSH 클라이언트가 '개인키 파일의 권한이 너무 열려 있다'는 이유로 접속을 거부합니다. 접속이 안 될 때는 ① 권한(600) ② 키 내용 복붙 과정에서 개행·공백이 깨지지 않았는지를 먼저 확인하세요.

PART Ⅱ

IaC 클라우드 인프라 구축 — Terraform 실습

Part Ⅰ에서 콘솔로 손수 만든 것과 똑같은 인프라(서브넷 조회, NIC, 인스턴스, 플로팅 IP)를 코드로 선언하고, terraform apply 명령 한 번으로 재현 가능하게 만듭니다.

01 · Terraform이란

Terraform은 클라우드 환경에서 인프라 관리를 단순화하는 오픈소스 코드 프로비저닝 도구입니다. 버전관리·재사용·공유가 가능한, 사람이 읽을 수 있는 구성 파일로 클라우드 및 온프레미스 리소스를 모두 정의할 수 있는 코드형 인프라(IaC) 도구입니다. 일관된 워크플로우를 사용해 수명주기 전반에 걸쳐 모든 인프라를 프로비저닝·관리할 수 있으며, 컴퓨팅·스토리지·네트워킹 같은 하위 수준 구성요소는 물론 DNS 항목 및 SaaS 기능 같은 상위 수준 구성요소도 관리할 수 있습니다.

💬쉽게 말하면

Terraform 코드는 집을 지을 때의 "설계도"와 같습니다. 설계도(코드)에 몇 층짜리 건물을 어떤 구조로 지을지 적어두면, terraform apply는 그 설계도대로 실제 시공을 진행하는 것이고, terraform destroy는 지은 건물을 다시 철거하는 것입니다. 설계도만 잘 보관해 두면 언제든 같은 건물을 다시 짓거나, 다른 부지에 똑같이 지을 수 있습니다 — Part Ⅰ에서 콘솔로 직접 클릭해 지었던 것과 결과물은 같지만, 이번엔 그 과정을 문서(코드)로 남기는 것이 다릅니다.

?왜 콘솔 클릭 대신 코드로 인프라를 관리하는가

Part Ⅰ에서 직접 겪었듯, 콘솔 클릭은 '무엇을 몇 번, 어떤 값으로 클릭했는지'가 기록에 남지 않아 재현이 어렵고, 사람이 인스턴스 5대를 만들다 보면 오타나 순서 누락 같은 실수가 생기기 쉽습니다. Terraform은 이 모든 절차를 코드(버전관리 가능한 텍스트 파일)로 선언해 두고, terraform apply 한 번으로 동일하게 재현하거나 terraform destroy 한 번으로 깨끗이 제거할 수 있게 합니다.

◎실무에서 어떤 상황에 적용되는가

여러 교육생에게 동일한 5대 클러스터 환경을 반복 배포해야 하는 이 실습 자체가 대표적인 사례입니다. 실무에서는 신규 프로젝트 환경 구성, 재해복구(DR) 환경 복제, 스테이징·운영 환경 동기화 등에 널리 쓰입니다.

Terraform CLI는 인프라를 코드로 정의(IaC)하고 배포·관리하는 데 사용하는 명령줄 도구입니다. 코드의 유효성을 검증하고, 실제 배포 전 변경사항을 미리 예측하며, 안전하게 인프라를 생성·삭제하는 것이 핵심 특징입니다. 기본 형태는 terraform [global options] subcommand [args] 입니다.

명령어의미

terraform apply인프라 배포(생성/변경)
terraform destroy생성된 인프라 삭제
◎실무에서 어떤 상황에 적용되는가

이 6개 명령어는 실습에서만 쓰고 끝나는 것이 아니라, 실무에서 인프라를 변경할 때 밟는 표준 절차 그 자체입니다. 예를 들어 팀에서 코드 리뷰(PR) 시점에는 terraform plan 결과를 첨부해 '무엇이 바뀌는지'를 함께 검토하고, 병합 후 배포 파이프라인에서 terraform apply를 자동 실행하는 식으로 CI/CD에 그대로 편입됩니다.

⚙왜 반드시 init → validate → plan → apply 순서인가

init은 코드에서 선언한 프로바이더(openstack) 플러그인을 내려받아 이 코드를 실행할 수 있는 상태로 만듭니다. validate는 문법 오류를 걸러내고, plan은 '지금 코드와 실제 클라우드 상태를 비교했을 때 무엇이 새로 생성·변경·삭제될지'를 미리 계산해 사람이 검토할 기회를 줍니다. apply는 그 계획을 실제로 실행합니다. 이 미리보기(plan) 단계가 있기 때문에, 오히려 콘솔에서 클릭 몇 번으로 바로 실행되는 것보다 더 안전하게 대규모 인프라를 변경할 수 있습니다.

아래는 init → validate → plan → apply 순서대로 실행했을 때 실제 화면에 나타나는 출력이다.

bash
$ terraform init Initializing provider plugins found in the configuration... - Finding terraform-provider-openstack/openstack versions matching "~> 1.42.0"... - Installing terraform-provider-openstack/openstack v1.42.0... - Installed terraform-provider-openstack/openstack v1.42.0 (self-signed, key ID 4F80527A391BEFD2)…

실제 실습 결과 코드에 선언된 openstack 프로바이더 플러그인을 내려받아 설치하는 화면이다.

bash
$ terraform validate Success! The configuration is valid.

실제 실습 결과 문법 오류가 없으면 이 한 줄만 출력된다.

bash
$ terraform plan data.openstack_networking_secgroup_v2.nhn-sg: Reading... data.openstack_networking_network_v2.nhn-network: Reading... data.openstack_images_image_v2.ubuntu_focal: Reading... data.openstack_networking_network_v2.ext_network: Reading... …

실제 실습 결과 main.tf의 data 블록들을 하나씩 조회(Reading)한 뒤, 무엇이 새로 생성될지 계획을 보여준다.

bash
$ terraform apply data.openstack_images_image_v2.ubuntu_focal: Reading... data.openstack_networking_secgroup_v2.nhn-sg: Reading... data.openstack_networking_network_v2.ext_network: Reading... data.openstack_networking_network_v2.nhn-network: Reading... …

실제 실습 결과 plan과 동일하게 기존 리소스부터 조회한 뒤, 이어서 실제 인프라 생성이 진행된다(원본 자료에는 이후 로그가 이어지지 않는다).

💬쉽게 말하면

내비게이션에 비유하면, plan은 출발 전 "예상 경로를 미리 보여주는 화면"이고 apply는 실제로 "출발해서 그 경로대로 운전하는 것"입니다. 경로를 미리 확인하지 않고 바로 출발하면 원치 않는 곳으로 갈 수도 있듯, plan 없이 바로 apply부터 하면 의도치 않은 변경이 실제로 적용될 위험이 있습니다.

03 · Terraform 파일 구성과 변수 매핑

?왜 파일 하나에 다 적지 않고 4개로 나누는가

provider.tf(인증정보)·main.tf(리소스 정의)·variables.tf(변수 선언)·terraform.tfvars(변수 값)를 분리해두면, 코드 구조(main.tf)와 환경별로 달라지는 값(tfvars), 그리고 절대 공유되면 안 되는 인증정보(provider.tf)의 관심사가 분리됩니다. 그 결과 main.tf는 한 번만 작성해 두고 tfvars만 바꿔서 여러 교육생·여러 환경에 동일한 코드를 재사용할 수 있습니다.

💬쉽게 말하면

요리 레시피에 비유하면, variables.tf는 "어떤 재료가 필요한지 목록"만 적어둔 것이고, terraform.tfvars는 그 목록에 맞춰 "실제로 장 봐온 재료"를 채워 넣은 것입니다. main.tf는 재료 이름이 아니라 "재료 목록의 몇 번"을 쓰라고 적어둔 조리법이라서, 재료(tfvars)만 바꿔 끼우면 같은 조리법(main.tf)으로 다른 요리(다른 교육생의 환경)를 만들 수 있습니다. provider.tf는 이 모든 걸 시작하기 전에 필요한 "출입 신분증"(인증 정보)이라고 보면 됩니다.

파일역할
provider.tf프로바이더 인증정보 및 기본 리전 설정
main.tf인프라의 핵심이 되는 실제 자원(resource)과 조회(data)를 정의
variables.tf프로젝트에서 사용할 변수의 이름·타입·설명을 정의(선언)
terraform.tfvarsvariables.tf에서 선언한 변수에 실제 값(value)을 대입

이 코드가 하는 일을 한 줄로 요약하면: 위 4개 파일이 실제 프로젝트 폴더 안에서 어떤 이름·구조로 놓이는지 보여주는 예시입니다.

project/
├── README.md
├── main.tf              # 인프라의 핵심이 되는 실제 자원과 데이터를 정의
├── variables.tf         # 사용할 변수들의 목록과 타입, 기본값 등을 정의
├── terraform.tfvars     # 변수들의 실제 값(Value)을 정의
└── provider.tf          # 프로바이더 인증정보 및 기본 리전 설정

Terraform 명령어를 실행하면 실행한 위치의 모든 .tf 파일을 읽어서 실행합니다.

⚙변수 매핑이 실제로 어떻게 연결되는가
# ① 변수 선언 (variables.tf)
variable "vpc_name" {
  description = "vpc 이름"
  type        = string
}

# ② 변수값 매핑 (terraform.tfvars)
vpc_name = "Default Network"

# ③ 변수 사용 (main.tf)
data "openstack_networking_network_v2" "nhn-network" {
  name = var.vpc_name
}

# ④ 결과 — Terraform이 실행 시점에 내부적으로 치환
data "openstack_networking_network_v2" "nhn-network" {
  name = "Default Network"
}

variables.tf가 '이런 이름의 변수가 있다'를 선언하고, terraform.tfvars가 그 변수에 실제 값을 채워 넣으면, main.tf 안의 var.vpc_name은 실행 시점에 "Default Network"로 치환됩니다. main.tf 자체는 절대 값이 바뀌지 않아도, tfvars 파일만 바꿔 끼우면(예: 교육생마다 다른 subnet_name) 완전히 다른 환경에 똑같은 코드를 재사용할 수 있습니다.

!보안 주의

provider.tf에는 tenant_id, password 같은 실제 인증 정보가 그대로 들어갑니다. 이런 파일은 절대 Git 같은 공개 저장소에 커밋하면 안 됩니다 — 실습 시 provider.tf를 .gitignore에 추가하거나, 인증값 자체를 tfvars/환경변수로 분리해 관리하는 습관을 들이세요. 아래 provider.tf 예시는 실제 계정 값 대신 자리표시자(placeholder)로 작성되어 있습니다.

이 코드가 하는 일을 한 줄로 요약하면: Terraform이 NHN Cloud(OpenStack API)에 접속할 때 쓸 계정 인증 정보와, 사용할 프로바이더(플러그인) 버전을 지정하는 설정 파일입니다.

terraform {
  required_version = ">= 1.0.0"
  required_providers {
    openstack = {
      source  = "terraform-provider-openstack/openstack"
      version = "~>1.42.0"
    }
  }
}
provider "openstack" {
  tenant_id  = "{테넌트ID}"
  password   = "{API 비밀번호}"
  auth_url   = "{신원서비스 URL}"
  user_name  = "{NHN 계정입력}"
  region     = "{리전}"
}

04 · main.tf 리소스 정의 상세

Data 블록은 OpenStack에 이미 존재하는 리소스(VPC, Subnet, Security Group, 이미지, 외부 네트워크)를 조회하기 위한 Data Source 정의이고, Resource 블록은 Terraform이 새로 생성·관리할 인프라 객체를 정의합니다.

Data 블록조회 대상비고
openstack_networking_network_v2.nhn-network기존 VPC(Network)name = var.vpc_name
openstack_networking_subnet_v2.nhn-subnet특정 VPC 내부의 Subnetnetwork_id는 위 nhn-network의 id를 참조, name = var.subnet_name
openstack_networking_secgroup_v2.nhn-sgSecurity Groupname = var.security_groups_name
openstack_images_image_v2.ubuntu_focalOS 이미지name = "Ubuntu Server 22.04.5 LTS (2026.03.10)"(이미지 이름은 변수화하지 않고 그대로 사용), most_recent = var.boolean_type_true로 동일 이름 중 최신 이미지 선택
openstack_networking_network_v2.ext_networkPublic Network(외부망)name = var.network_type_public
Resource 블록역할
openstack_networking_port_v2.nicVM이 사용할 네트워크 인터페이스(NIC/Port) 생성 — network_id, fixed_ip.subnet_id, security_group_ids 지정
openstack_compute_instance_v2.instance1VM(인스턴스) 생성 — name/availability_zone/flavor_name/key_pair + block_device(부팅 볼륨: uuid=이미지ID, source_type="image", destination_type="volume", delete_on_termination, volume_size, volume_type) + network.port=위에서 만든 nic
openstack_networking_floatingip_v2.fip_1Public Network(pool)에서 플로팅 IP 생성
openstack_compute_floatingip_associate_v2.fip_1생성한 플로팅 IP를 instance1에 연결(wait_until_associated로 연결 완료까지 대기)
⚙data와 resource는 무엇이 다른가

data는 OpenStack에 이미 존재하는 것(기존 VPC, 기존 이미지, 기존 보안그룹)을 '조회만' 해서 ID를 가져오는 블록이고, resource는 Terraform이 새로 '만들고 관리'할 대상(NIC, 인스턴스, 플로팅 IP)을 정의하는 블록입니다. Part Ⅰ 콘솔 실습에서 서브넷·보안그룹처럼 이미 있는 것을 '선택'만 했던 부분이 data로, 인스턴스처럼 새로 '생성'했던 부분이 resource로 그대로 대응됩니다.

◎실무에서 어떤 상황에 적용되는가

이미 다른 팀이 만들어 둔 VPC·보안그룹·이미지를 그대로 활용하면서 그 위에 내 리소스만 새로 얹어야 하는 상황(공용 네트워크 팀과 애플리케이션 팀이 분리된 조직 등)에서 data/resource 구분이 그대로 쓰입니다. 이 실습에서 VPC·서브넷·보안그룹·이미지·외부망을 전부 data로 조회만 한 것도, 그 자원들은 관리자가 미리 만들어 둔 공용 자원이고 교육생은 그 위에 NIC·인스턴스·플로팅 IP만 새로 만들면 되기 때문입니다.

05 · 실습1 — 하드코딩 버전 (인스턴스 1대)

?왜 이 작업을 하는가

처음에는 일부러 변수 없이 값을 코드에 직접 적어(하드코딩) 작성합니다. Terraform 문법 자체(블록 구조, data를 resource에서 참조하는 방식)에 먼저 익숙해지기 위한 디딤돌이며, 다음 실습2에서 이 값들을 변수로 바꿔볼 때 '무엇이, 왜 불편했는지'를 비교할 기준이 됩니다.

  1. provider.tf 작성

    본인이 발급받은 테넌트ID/비밀번호/인증URL/계정/리전 입력.

  2. main.tf의 data 5개 작성(값 하드코딩)

    nhn-network name="Default Network", nhn-subnet name="Default", nhn-sg name="default", ubuntu_focal name="Ubuntu Server 22.04.5 LTS (2026.03.10)" + most_recent=true, ext_network name="Public Network".

  3. main.tf의 resource 4개 작성

    nic(name="nhn-nic01"), instance1(name="k8s-master", availability_zone="kr-pub-a", flavor_name="m2.c4m8", key_pair="sesac-key", block_device{volume_size=50, volume_type="General HDD", ...}), fip_1(플로팅 IP 생성 + instance1에 연결).

  4. 실행

    terraform init → terraform plan → terraform apply 순서로 실행.

이 코드가 하는 일을 한 줄로 요약하면: 기존 VPC·서브넷·보안그룹·이미지·외부망을 조회한 뒤, 그 위에 인스턴스 1대(Control Plane)와 그 인스턴스에 연결할 네트워크 인터페이스·플로팅 IP를 만드는 전체 main.tf입니다. 값은 아직 전부 문자열로 직접 적혀(하드코딩) 있습니다.

data "openstack_networking_network_v2" "nhn-network" {
  name = "Default Network"
}
data "openstack_networking_subnet_v2" "nhn-subnet" {
  network_id = data.openstack_networking_network_v2.nhn-network.id
  name = "Default"
}
data "openstack_networking_secgroup_v2" "nhn-sg" {
  name = "default"
}
data "openstack_images_image_v2" "ubuntu_focal" {
  name = "Ubuntu Server 22.04.5 LTS (2026.03.10)"
  most_recent = true
}
data "openstack_networking_network_v2" "ext_network" {
  name = "Public Network"
}

resource "openstack_networking_port_v2" "nic" {
  name = "nhn-nic01"
  network_id = data.openstack_networking_network_v2.nhn-network.id
  fixed_ip {
    subnet_id = data.openstack_networking_subnet_v2.nhn-subnet.id
  }
  security_group_ids = [
    data.openstack_networking_secgroup_v2.nhn-sg.id
  ]
}

resource "openstack_compute_instance_v2" "instance1" {
  name              = "k8s-master"
  availability_zone = "kr-pub-a"
  flavor_name       = "m2.c4m8"
  key_pair          = "sesac-key"
  block_device {
    uuid                  = data.openstack_images_image_v2.ubuntu_focal.id
    source_type           = "image"
    destination_type      = "volume"
    delete_on_termination = true
    volume_size           = 50
    volume_type           = "General HDD"
  }
  network {
    port = openstack_networking_port_v2.nic.id
  }
}

resource "openstack_networking_floatingip_v2" "fip_1" {
  pool = data.openstack_networking_network_v2.ext_network.name
}
resource "openstack_compute_floatingip_associate_v2" "fip_1" {
  floating_ip = openstack_networking_floatingip_v2.fip_1.address
  instance_id = openstack_compute_instance_v2.instance1.id
  wait_until_associated = true
}

이 코드가 하는 일을 한 줄로 요약하면: 위에서 작성한 코드를 초기화(init) → 미리보기(plan) → 실제 배포(apply)까지 순서대로 실행하는 명령 3줄입니다.

$ terraform init
$ terraform plan
$ terraform apply

07 · 실습3(과제) — 인스턴스 5대로 확장

Terraform 실습 두 번째에서 작성한 파일에서 인스턴스 개수를 4개 더 작성하여 총 5대의 인스턴스를 배포하는 테라폼 파일을 작성하시오. (Master 1대, Worker 3대, NFS 1대) — 원본 과제 문구

?왜 이 작업을 하는가

resource 블록은 기본적으로 '블록 하나 = 리소스 하나'입니다. 역할이 다른 서버(master / worker1~3 / nfs)를 각각 만들려면 nic/instance 블록을 필요한 만큼 복사해 이름(레이블)만 바꿔 반복 작성해야 합니다. (규모가 훨씬 크다면 count/for_each로 반복을 줄일 수 있지만, 이 실습에서는 노드마다 역할이 달라 개별 블록으로 명시적으로 작성합니다.)

  1. NIC 블록 추가

    nic2~nic5 블록 추가 — 각각 name = var.nic_name[n], 나머지는 nic과 동일하게 network_id/subnet_id/security_group_ids 참조.

  2. Worker 인스턴스 블록 추가

    instance2~instance4(worker1~3) 블록 추가 — name = var.worker_node[n], flavor_name/availability_zone/key_pair/block_device는 master와 동일, network.port만 각자의 nic을 참조.

  3. NFS 인스턴스 블록 추가

    instance5(nfs) 블록 추가 — name = var.nfs_server.

  4. 플로팅 IP는 master 전용
